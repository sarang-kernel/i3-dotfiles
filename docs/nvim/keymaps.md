# Keymaps

The leader key is **Space**; the local leader is `//`, and VimTeX uses `,`. This table is generated by reading the keymap definitions in my Lua files, so it lists exactly what is defined. Plugin defaults (Telescope's insert-mode keys, Neo-tree's own mappings, `gc` comments, Neovim's built-ins) are not listed because I did not define them; `:Telescope keymaps` or `<leader>?` shows everything that is live.

## Things worth knowing

- `<leader>gf` is defined **twice**: in `vim-options.lua` (`vim.lsp.buf.format`) and again in `none-ls.lua` (`vim.lsp.buf.format({ async = true })`). The later definition (none-ls, loaded lazily on file open) wins once a file is open.
- `gf` on a Markdown file is remapped for `[[wiki links]]`: it opens `~/notes/<link>.md` (creating it if it does not exist). The README note about `gf` as file-under-cursor applies to every other filetype.
- **The git keymaps are not active.** `]c`, `[c`, `<leader>hs`, `<leader>hr`, `<leader>hP` and `<leader>hb` are written inside `M.setup_gitsigns_keymaps(bufnr)` in `vim-options.lua`, but nothing ever calls that function (`gitsigns.lua` has no `on_attach`). I checked in a headless session: `maparg("<leader>hs", "n")` is empty in a git file. The signs in the gutter work; the hunk keys do not. The fix is one line: `on_attach = require("vim-options").setup_gitsigns_keymaps` in the gitsigns options. The README table that lists them describes the intention, not the current state.
- The debug keymaps (`<leader>d…`) are registered by `nvim-dap-ui`'s config, so they appear once that plugin has loaded.
